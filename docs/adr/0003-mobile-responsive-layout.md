# ADR 0003: モバイルブラウザ対応のレイアウト方針

## Status
Accepted

## Context
スマホブラウザからアプリを利用できるようにするため、既存のデスクトップ専用レイアウト（固定サイドバー）をモバイル対応に拡張する必要が生じた。

Figma プロトタイプで以下の設計を検証済み：
- ナビゲーション: ボトムタブバー（4項目）
- 求人追加: FAB（フローティングアクションボタン、右下固定）
- 比較画面: 行=求人・列=評価軸に転置し、左列（求人名）固定・評価軸列を横スクロール

## Decision

### 1. 切り替え方式: CSS のみ（`md:` Tailwind プレフィックス）
`useMediaQuery` などの JS による viewport 検知は採用しない。Tailwind の `md:` プレフィックスで show/hide を制御する。

### 2. タブバー配置: `position: fixed bottom-0`
ボトムタブバーは `fixed bottom-0` で画面下部に固定する。`<main>` に `pb-[83px] md:pb-0` を付与してコンテンツが隠れないようにする。

### 3. FAB: フォームルートでは非表示
`/jobs/new` および `/jobs/:id/edit` では `useLocation` で現在パスを検知し FAB を隠す。フォーム画面上で「求人追加」を促す必要がないため。

### 4. 比較画面: 1ファイルに2 JSX ブロック
デスクトップ用 JSX（`hidden md:flex`）とモバイル用 JSX（`md:hidden`）を `Compare.tsx` に同居させる。スコア計算・データ取得ロジックを分割せず共有するため。

## Rationale

**CSS のみを選んだ理由**: このアプリはブラウザ専用（SSR なし）なので JS の viewport 検知に技術的な必要性がない。`md:` クラスはすでにプロジェクト内で使われており（`sm:grid-cols-2` など）統一感がある。

**`fixed` 配置を選んだ理由**: 各ページが `h-full / overflow-y-auto` で独自にスクロールを管理しており、flex 組み込みにするとすべてのページのスクロール実装を見直す必要が生じる。`fixed` なら `<main>` の padding 変更のみで済む。

**比較画面を1ファイルに2 JSX で持つ理由**: スコア取得・合致度計算・最高スコア判定はすでに複雑なロジックを含む。コンポーネントを分割するとロジックの共有に props drilling や Context が必要になりコストが増す。JSX の2系統化で対処する。

## Consequences
- `Layout.tsx` に `aside`（デスクトップ）とボトムタブ+FAB（モバイル）の両方が存在する
- `Compare.tsx` のモバイル用 JSX は行=求人・列=評価軸（CONTEXT.md の定義に合わせて更新済み）
- 将来タブレット向けに第3のブレークポイントを加える場合は本 ADR の方針に従い CSS クラスで対応する
